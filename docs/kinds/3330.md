# Kind 3330 — Call signal (Chatme custom)

**Status:** private Chatme convention, not a NIP. It only has meaning for Chatme clients that implement the same signal types.

**Purpose:** carry WebRTC signaling between two Chatme users over Nostr relays, without a dedicated signaling server.

**Transport:** a kind `3330` rumor inside the standard NIP-17 envelope: seal kind `13`, gift wrap kind `1059`, NIP-44 encryption. See the [kind index](README.md) for the shared envelope and validation rules.

## Rumor shape

| Field | Value |
| --- | --- |
| `kind` | `3330` |
| `pubkey` | Sender's public key (caller or callee, depending on the signal). |
| `created_at` | Unix seconds. Freshness is checked by the receiver. |
| `tags` | `p` = recipient's 64 lowercase hex public key. Call signals do not use `e` tags. |
| `content` | A JSON **string**, not a JSON object. Parsing yields a map with `type` plus optional `data` and `seq`. |
| `id` | NIP-01 sha256 of `[0, pubkey, created_at, kind, tags, content]`. No `sig` on the rumor. |

Illustrative rumor for an offer:

```json
{
  "pubkey": "<caller 64-hex pubkey>",
  "created_at": 1760000200,
  "kind": 3330,
  "tags": [["p", "<callee 64-hex pubkey>"]],
  "content": "{\"type\":\"offer\",\"data\":\"v=0 o=- ... a=candidate ...\"}",
  "id": "<64-hex sha256 event id>"
}
```

The decoded `content` map is the actual signal:

```json
{ "type": "offer", "data": "v=0 o=- ... a=candidate ..." }
```

## Signal types

| `type` | `data` | `seq` | Meaning |
| --- | --- | --- | --- |
| `offer` | Final SDP offer | No | Caller starts a call. ICE candidates are gathered into the SDP before sending (vanilla ICE), so there is no trickle burst. |
| `ringing` | Absent | No | Callee acknowledges the offer and moves the caller to the ringing state. |
| `answer` | Final SDP answer | Optional | Callee answers an offer. `seq` is present for an ICE-restart answer. |
| `restart_offer` | Final SDP offer | Yes | Caller proposes an ICE restart with an increasing sequence number. |
| `candidate` | ICE candidate | No | Handler exists for this type. The current main WebRTC path embeds candidates in the SDP instead of sending standalone candidates. |
| `hangup` | Absent | No | Either side ends or declines the call. |

`seq` is only part of the ICE-restart flow. Plain offers and answers do not need it.

## Send and receive behavior

- `RelayManager.sendCallSignal` builds the wrap and broadcasts it to all connected relays that are up. The foreground path uses the isolate wrapper; the background hangup path builds the same kind of rumor directly.
- Only `offer` wakes the receiver's device through a push notification. Other signals stay relay-only, except that a caller's `hangup` while the caller is not connected also asks the receiver's device to dismiss the ringing notification.
- A receiver drops a signal when its age is more than 30 seconds for `offer`, or more than 60 seconds for any other type. It also drops an event more than 60 seconds in the future.
- `answer`, `candidate` and `restart_offer` are ignored when there is no active call. `offer` and `ringing` are allowed to route into call setup.
- The callee's final answer is sent only after ICE gathering finishes or a short wait expires, so the SDP normally contains the candidates.

## Compatibility and limits

- WebRTC signaling has no Nostr standard. Another client cannot assume any of these `type` values or SDP layouts.
- The `data` string is SDP or an ICE candidate produced by `flutter_webrtc`. It is not a portable JSON description of a session.
- Delivery is best-effort. A lost `ringing` or `hangup` can leave UI state behind; the call layer has its own timeouts.
- The gift wrap hides the sender and content from relays, but the `p` tag still tells the relay which account the wrap is for.
