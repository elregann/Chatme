# Kind 3331 — Story post or retract (Chatme custom, prototype)

**Status:** Chatme prototype, not a NIP. Nostr has no standard story kind yet, so this format is private to Chatme and may change.

**Purpose:** send a picture or video that disappears after 24 hours, or retract a previously sent story. Both shapes use the same inner rumor kind; the tags and content distinguish them.

**Transport:** a kind `3331` rumor inside the standard NIP-17 envelope: seal kind `13`, gift wrap kind `1059`, NIP-44 encryption. See the [kind index](README.md) for the shared envelope and validation rules.

Chatme sends one wrap per saved contact plus one to the author's own account. `Nip17.wrapMulti` builds **one** rumor first, so every envelope carries the same rumor id; only the seal and gift wrap differ per recipient. Stories are not group chat messages and do not use `e` reply tags.

## Story post

### Rumor shape

| Field | Value |
| --- | --- |
| `kind` | `3331` |
| `pubkey` | Author's public key. |
| `created_at` | Unix seconds, pinned by the sender so a retry keeps the same rumor id. |
| `content` | The `https` URL of the encrypted file on a Blossom server. The bytes are not in the Nostr event. |
| `id` | The story id: NIP-01 sha256 of `[0, pubkey, created_at, kind, tags, content]`. Must be 64 lowercase hex because it becomes a local filename. |
| `sig` | Absent. The seal authenticates the author. |

### Tags

| Tag | Required | Meaning |
| --- | --- | --- |
| `p` | Yes | Intended recipient. See the implementation note about duplication below. |
| `story` | Yes | `1`. This is the marker that separates a story post from other kind `3331` payloads. |
| `expiration` | Yes | Unix seconds. Chatme defaults to 24 hours after creation. |
| `file-type` | Yes | MIME type, for example `image/jpeg` or `video/mp4`. |
| `encryption-algorithm` | Yes | `aes-gcm` for pictures, `aes-gcm-chunked` for videos. |
| `decryption-key` | Yes | 64 hex characters. |
| `decryption-nonce` | Yes | 24 or 32 hex characters. |
| `x` | Yes | sha256 of the encrypted file, hex. |
| `ox` | No | sha256 of the original plaintext file, hex. |
| `size` | No | Encrypted file size in bytes. |
| `psize` | No | Plaintext file size in bytes. |
| `duration` | No | Media duration in seconds. |
| `dim` | No | `WIDTHxHEIGHT`, for example `1080x1920`. |
| `caption` | No | Trimmed caption text. |

The file tags are the same layout Chatme uses for normal kind `15` file messages. Chatme's local file map names the algorithm field `alg`, but the wire tag is `encryption-algorithm`. Other clients should not assume they can open `aes-gcm-chunked`; that chunked layout is Chatme-specific.

Illustrative post rumor:

```json
{
  "pubkey": "<author 64-hex pubkey>",
  "created_at": 1760000300,
  "kind": 3331,
  "tags": [
    ["p", "<recipient 64-hex pubkey>"],
    ["expiration", "1760086700"],
    ["story", "1"],
    ["p", "<recipient 64-hex pubkey>"],
    ["file-type", "image/jpeg"],
    ["encryption-algorithm", "aes-gcm"],
    ["decryption-key", "<64-hex key>"],
    ["decryption-nonce", "<24-or-32-hex nonce>"],
    ["x", "<64-hex sha256 of encrypted bytes>"],
    ["ox", "<64-hex sha256 of original bytes>"],
    ["psize", "<plaintext byte count>"],
    ["dim", "1080x1920"],
    ["caption", "Weekend"]
  ],
  "content": "https://example.test/blob/<encrypted-file>",
  "id": "<64-hex story id>"
}
```

**Implementation note:** the current sender emits the `p` tag twice, once from `StoryEvent.buildTags` and once from `FileMessage.rumorTags`. Readers use the first matching tag for a given name, so the duplicate is harmless in Chatme, but it should not be treated as an intentional part of the format.

### Receiver behavior

1. Unwrap and verify the NIP-17 layers. The inner kind must be one of the kinds Chatme accepts.
2. Require a valid `story` tag and parse the content with the kind `15` file parser: `https` URL, supported algorithm, hex key/nonce/hash. Invalid rows are ignored.
3. Ignore stories from senders who are not saved contacts.
4. Ignore expired stories and ids already tombstoned by a retract.
5. Require a canonical 64 lowercase hex rumor id; otherwise it cannot be used safely as a filename.
6. Use `expiration` when present and sane; otherwise fall back to creation time plus 24 hours.
7. On replay of a known id, preserve local-only fields: already cached media path, view records and upload keypair.

## Retract

A retract reuses kind `3331` with a different shape. It carries no file and no `story` marker.

| Field | Value |
| --- | --- |
| `kind` | `3331` |
| `content` | The 64 lowercase hex id of the story being retracted. |
| `tags` | `p` = intended recipient, `story_delete` = the same story id, `expiration` = now plus 24 hours. |

Illustrative retract rumor:

```json
{
  "pubkey": "<author 64-hex pubkey>",
  "created_at": 1760000400,
  "kind": 3331,
  "tags": [
    ["p", "<recipient 64-hex pubkey>"],
    ["story_delete", "<64-hex story id>"],
    ["expiration", "1760086800"]
  ],
  "content": "<64-hex story id>",
  "id": "<64-hex sha256 event id>"
}
```

A receiver only honors a retract from a saved contact. If the story is present locally and its author matches the sender, Chatme deletes the local row and its cached media. It then stores a tombstone for the story id and author until the retract's `expiration`, so a relay replay of the original story cannot bring it back. No chat message is created.

## Local-only data

`viewedBy`, `localPath` and the upload keypair are local Hive fields. They are never part of kind `3331` and are never sent to relays. A view is reported separately by [kind 3332](3332.md). When media is cached locally, Chatme re-reads the stored row before writing `localPath`, so caching cannot overwrite a view that was just recorded.

## Compatibility and limits

- Other clients have no standard behavior for kind `3331`; they should ignore it.
- A story only reaches saved Chatme contacts and the author's own account. It is not public and is not addressed to a NIP-50 search result.
- An `aes-gcm-chunked` video is not openable by clients that only implement the plain file layout.
- Relays see only the gift wrap and its `p` tag. They do not see the caption, URL, key or story id from the rumor.
- Delivery is best-effort; there is no read acknowledgement for a story post or retract.
