# Kind 3329 — Read receipt (Chatme custom)

**Status:** private Chatme convention, not a NIP. It only has meaning for Chatme clients that implement it.

**Purpose:** tell the sender that one of their messages was read, so the sender's local message row can change to `read`. It is not a new chat message and is not displayed in the conversation.

**Transport:** a kind `3329` rumor inside the standard NIP-17 envelope: seal kind `13`, gift wrap kind `1059`, NIP-44 encryption. See the [kind index](README.md) for the shared envelope and validation rules.

## When it is sent

Chatme sends a receipt when a conversation is opened/read. The foreground send path is gated by the `read_receipts_enabled` setting (default on) and by having both a private key and a public key. The background path also checks that setting and caps a batch at the 20 most recent unread ids so a long backlog does not flood relays.

The receipt is sent for the **message/rumor id stored by Chatme**, not for the public gift wrap id.

## Rumor shape

| Field | Value |
| --- | --- |
| `kind` | `3329` |
| `pubkey` | Reader's public key. |
| `created_at` | Unix seconds, set when the rumor is built. |
| `tags` | `e` = target message id, `p` = recipient (the original message sender). Both values are 64 lowercase hex. |
| `content` | `read` in the current sender. The receiver trims the string and treats any non-empty value as the new status. |
| `id` | NIP-01 sha256 of `[0, pubkey, created_at, kind, tags, content]`. No `sig` on the rumor. |

Illustrative rumor after decrypting the two outer layers:

```json
{
  "pubkey": "<reader 64-hex pubkey>",
  "created_at": 1760000100,
  "kind": 3329,
  "tags": [
    ["e", "<target message 64-hex rumor id>"],
    ["p", "<original sender 64-hex pubkey>"]
  ],
  "content": "read",
  "id": "<64-hex sha256 event id>"
}
```

## Receiver behavior

1. Unwrap the NIP-17 gift wrap and verify the seal as for any other private message.
2. Take the first `e` tag as the target message id. Chatme's unwrapped result exposes this as `replyToId`.
3. Trim the rumor content and use it as the new status. Empty target or empty status is ignored.
4. Apply the status to the local message row in the chat identified by the seal sender and the local user.
5. Consume the event: it is not inserted into the message list and is not shown in the UI.

The `p` tag names the intended recipient, but this receive path identifies the conversation from the authenticated seal sender and the local account. A malformed receipt therefore cannot create a new conversation by itself.

## Compatibility and limits

- Other Nostr clients have no standard behavior for kind `3329`; they should ignore it.
- This is a best-effort signal. If every relay drops it, the sender's message simply stays unread locally.
- Turning read receipts off stops Chatme from sending them. It does not stop Chatme from applying receipts that arrive from someone else.
- Only the status string is carried. There is no timestamp field beyond the rumor's `created_at`, and no read count.
